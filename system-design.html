ENGINEERING / ARCHITECTURE NOTES

Tenant provisioning service

Accept now.
Provision asynchronously.

A small control plane that turns tenant requests into durable work, tracks their progress, and keeps state consistent when messages arrive twice, late, or out of order.

Python + FastAPISQLite WALRabbitMQ + PikaDocker Compose
→
The database owns the truth. The broker carries the work.

HTTP 202 means the tenant change and task are committed. The worker completes the operation later, and the client polls the API for the result.

01

Three services. One authority for state.

The API service contains the HTTP handlers and two background threads. A separate worker simulates provisioning. RabbitMQ connects them; only the API service accesses SQLite.

API service

Validates requests, enforces state and version rules, owns the database, publishes the outbox, and consumes results. Reads return the latest committed state.

Message broker

Buffers work across process restarts. Persistent messages, durable queues, publisher confirms, and manual acknowledgements support recovery.

Worker simulator

Produces progress with configurable delay and failure rate. Stable event IDs make redelivery safe for the control plane’s state changes.

02

The journey of one create request

  1. Validate the requestPOST /tenants supplies a unique slug and a name. Invalid bodies return 422; a reserved slug returns 409.
  2. Commit three recordsOne SQLite transaction inserts a provisioning tenant at version 1, an accepted deploy task, and its immutable outbox event.
  3. Return acceptanceAfter commit, the API returns 202, the tenant and task, and a Location header. Provisioning is still pending.
  4. Publish the taskThe background publisher reads committed outbox rows. It marks a row published only after RabbitMQ confirms receipt.
  5. Simulate provisioningThe worker emits in_progress, waits, then emits done or failed. It ACKs the task after confirming both result publications.
  6. Apply the resultThe result consumer commits its inbox receipt and state changes before ACKing. Success leaves the tenant active at version 2.
Why the transactional outbox matters

The accepted task and the intent to publish it cannot split apart. A database rollback leaves neither. A broker outage leaves the committed outbox row available for a later retry.

03

Two state machines, linked by a task

A tenant describes the resource. A task describes one asynchronous operation on that resource. The API starts an operation; progress events complete it.

Task lifecycle — every operation
accepted→in_progress→doneorfailed

A terminal result received before in_progress waits in the inbox. Terminal tasks never reopen.

OperationAllowed starting stateAPI transitionSuccessful result
Create / deployNo existing slugprovisioning · version 1active · version 2
PATCH / updateactive + matching versionupdating · version +1active · version +1
DELETE / destroyactive or faileddestroying · version +1destroyed · version +1

What changes the version?

An accepted update or destroy increments it. Applying a terminal result increments it once. Starting the task or receiving a duplicate leaves the tenant version unchanged. A successful create → update → destroy ends at version 6.

Failure and deletion

Any failed operation makes the tenant failed, with one version increment for that result. DELETE is allowed from failed. Destroyed tenants remain readable, and their slugs stay reserved.

    Two updates arrive. One wins.

    Both clients read an active tenant at version 2 and send PATCH with version: 2. SQLite’s BEGIN IMMEDIATE reserves the writer before checking the tenant, so validation and mutation happen under the same transaction.

    2. Read the new tenant version 3.
    3. Compare the submitted version 2 with 3.

    409 tenant_version_conflict

    Version validation runs before the state guard, so the loser receives a version conflict even though the tenant is now updating. If the write lock cannot be acquired within five seconds, the API returns 503. The live smoke test exercises 12 clients: one accepted update and 11 conflicts.

    06

    Four tables make recovery explicit

    One tenant has many tasks. Every task has exactly one outbox record created with it and can have many inbox receipts. Foreign keys preserve these relationships.

    tenants

    • id — UUID primary key
    • slug — unique, immutable, never reused
    • name, status, version
    • created_at, updated_at

    The current resource state and optimistic concurrency token.

    tasks → tenants

    • id — UUID primary key
    • tenant_id — tenant foreign key
    • type, status
    • created_at, updated_at

    The operation history. HTTP access is read-only.

    outbox → tasks

    • task_id — primary key + foreign key
    • payload — immutable task JSON
    • published_at — null until confirmed

    A durable publication intent, inserted inside the API transaction.

    inbox → tasks

    • sequence — ordered receipt key
    • event_id — unique progress UUID
    • task_id, status, received_at
    • disposition — pending / applied / ignored

    Deduplication and buffering for results that overtake their start event.

    Identity is part of the protocol

    The worker derives each progress UUID from the task ID and status, so redelivery regenerates the same identity. An existing event ID with different task or status is poison. For conflicting terminal receipts, the first stored receipt wins.

    07

    Recovery happens at the commit boundaries

    The system provides at-least-once message delivery with idempotent state updates. It does not claim exactly-once physical delivery across SQLite and RabbitMQ.

    Failure or ordering caseWhat survivesHow the system responds
    Broker unavailable after API commitTenant, task, unpublished outbox rowThe API can accept work while the database is available. The publisher reconnects and retries; readiness reports 503.
    Crash after publish confirmation, before outbox markBroker message plus still-pending outbox rowThe publisher may send the same task again. Stable progress IDs and inbox deduplication prevent repeating a terminal state change.
    Worker exits before task ACKThe broker’s unacknowledged taskConnection close requeues the delivery. A fresh worker can finish it. SIGINT and SIGTERM stop the simulator gracefully.
    Result committed, then crash before ACKInbox receipt and updated task/tenantThe broker redelivers. The duplicate receipt is recognized, no state is changed, and the result is ACKed.
    Terminal result arrives before startA pending terminal inbox receiptACK after storing it. When in_progress arrives, apply start and the first pending terminal result atomically.
    Late result for an already terminal taskThe completed task and any newer workRecord a fresh receipt as ignored. The old operation cannot change the tenant again.
    Invalid message or conflicting event identityThe rejected message in the matching dead-letter queue, when routing succeedsNACK with requeue=false; route through control.dead to control.tasks.dead or control.results.dead.
    Transient AMQP or database errorUnacknowledged deliveries and committed dataClose the connection, then reconnect with exponential backoff from 250 ms to a 10 s base delay, plus jitter.

    A pending terminal receipt requires an eventual start message. The simulator sends both; a manually injected terminal-only event intentionally leaves the task accepted.

    09

    The boundaries of this implementation

    The assignment is a local, single-instance control plane. These choices keep the implementation understandable while making its failure behavior explicit.

    SQLite and one publisher keep coordination simple

    WAL allows concurrent reads, while writes serialize. Run one API process with one outbox publisher. Scaling to multiple API replicas needs a shared database such as PostgreSQL, row-level concurrency control, and claimed outbox batches.

    Durability does not provide high availability

    Named volumes preserve state across ordinary container restarts and make down. A single broker and a local database are still single points of failure. Classic-queue dead lettering can lose a message if its target is unavailable; a production design could use replicated quorum queues and at-least-once dead lettering.

    State deduplication does not make external side effects exactly once

    The worker simulates work; it does not provision infrastructure. A real provider integration must make its actions idempotent using the task ID. A task can be redelivered and executed again even when duplicate results cannot change the tenant twice.

    The API is the assignment’s user interface

    No separate frontend is required. The root URL / redirects to Swagger at /docs for interactive API access. This HTML guide explains the design and operates independently of the service.

    Production features remain explicit follow-up work

    Authentication, authorization, rate limits, schema migrations, retention, cancellation, automatic retry of failed tasks, and operational alerting are not implemented. POST does not accept an idempotency key; duplicate slugs return a conflict. Updated names are retained if simulated work fails. The local broker’s guest credentials are for the assignment environment.
